# Events v2 — Phase 1C Sorteos

Events reuses RaffleStore's actual free, poll and visual_key machines with typed STAGE/SPEAKER/PLAYER grants. It does not invoke legacy raffle socket handlers or impersonate their roles. PLAYER can configure a prepared visual key, open, close entry intake, draw, manually reveal, close and reset prior winners at the engine's valid states. Público enters/votes using the server grant's participant and event-saved name; correction persists, blank preserves, rejected entry rolls it back. Free entries deduplicate identity across windows/reconnect; poll accepts one response; visual choice remains editable until close and evaluates the configured key then. Bystanders never enter automatically.

Migration 041 stores private raffle session snapshots in separate Events SQL, keyed by canonical LiveSession and bound to stage/activity/deck/version/catalog digest. Explicit open/configuration creates state; reads/reconnect never create a run. Each command decodes a fresh RaffleStore, performs pure transitions, writes a portable JSON parameter on the grant's existing transaction connection, and only acknowledges/fanouts after commit. Snapshot serialization reconstructs Maps/Sets, tickets, pending winner, reveal deadline and previous-winner exclusion. Stored pending choice is never resampled. No nominal global history, import or export API is exposed. Individual FKs are supplemented by server ownership/binding checks. Whole snapshots are suitable for this functional adapter; capacity/efficient high-volume persistence remains unverified.

The trusted prepared reader must match event/live/deck/version. Definition normalization rejects invalid modes, duplicate choices, bad visual keys and legacy media references rather than silently repairing them. Text/label fixtures only until private media assets are prepared. Production readers remain absent, with no public/demo fallback; Events stays off.

Presence is a fresh SQL-authorized view of currently connected sockets with fixed event/live binding. GrantRepository.sessionOn validates grant, issuer, resources and short session on the already locked connection, without a nested pool/transaction. The same organization lock covers selection and competing revoke/access changes. Draw includes only eligible entries whose participant is currently connected and authorized for that live, deduplicating windows. Production choice uses crypto.randomInt over that eligible population, then persists the selected entry before any emission. Reconnection preserves the choice/deadline. At automatic/manual reveal the pending participant must still be authorized and connected; otherwise the choice remains private in drawing, no replacement is sampled, and the controller may close or wait for valid recovery. Timing is five seconds; existing explicit manual reveal remains available earlier when authorized. Timers reauthorize bounded recent credential witnesses, prefer current controllers and can resume from a fresh authorized snapshot.

Controller projections retain operational entry/eligibility/poll counts without internal actor IDs or an early pending name. PLAYER gets Screen DTO, no roster, private results or winner history; visual collecting shows the deliberately marked option, as required by that mode. After reveal, Screen gets only winner name/label/ticket. Público gets only its own entry/selection and isWinner flag, with no other identities, roster, entry key, aggregates or history. Every recipient revalidates current permissions, live access and preparation. No raw room broadcast.

Socket commands: events:raffle:snapshot, configure_key {definitionId,optionId}, open {definitionId}, enter/submit_poll_response {raffleRunId,optionId?,name?}, close_entries/draw/reveal/close/reset_winners {raffleRunId}. Only the server-prepared definition is selected; client mode/config/actor/list/timestamps are not accepted. Run IDs reject stale/cross-execution commands. No legacy raffle events, external registration/list imports or fabricated histories.

Raffles, polls, contests and assessments exclude each other within a LiveSession through the shared queue and authorization transaction; Q&A coexists. Raffle snapshot durability does not claim durable poll state, full Live restart, general command idempotence, uncertain COMMIT or distributed scheduling; Phase 3 remains open. Keyboard/menu/consoles, private preparation/publication, remaining families and HTTP/media/export boundaries are still pending. Temporal only, no Main/Beta/Production merge/deploy; show.immersalive.com DNS is not needed yet.
